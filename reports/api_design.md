# FastAPI Backend — Design & Verification (Step 23)

*Deliverable: `src/api/main.py` (+ `src/api/diff_parsing.py`,
`ml_features.py`, `ml_model.py`, `llm_review.py`) — a `POST /review` endpoint
wrapping the best Experiment 2 model (fast, ML-only mode) and Experiment 4's
best LLM config (deep mode). Tests: `tests/test_api_*.py`, 43 tests. Verified
by running a live `uvicorn` server and hitting it with `curl` — see §6.*

---

## 1. What the endpoint does

`POST /review` takes a unified diff (+ optional title/description/commit
messages/repo) and returns:

* **`merge_probability`** / **`merge_prediction`** — always computed, from
  the trained Experiment 2 model. Free, instant, no network call.
* **`review_comments`** — only in `mode="deep"`: generated by a live call to
  Experiment 4's best-performing LLM config. `null` in `mode="fast"`
  (the default).

This is the literal reading of plan §7.1: *"a `fast` mode (ML-only, instant,
free) and a `deep` mode (adds the LLM pass)"* — the LLM augments the ML
result, it does not replace it. Merge probability is never something the
project asks an LLM to be the sole source of, and Experiment 3/4 already
showed the LLM's raw merge-prediction accuracy rarely beats the base rate
(`reports/exp3_model_evaluation.md`, `reports/exp4_model_evaluation.md` §1.1)
— routing it through the trained RF model instead is both cheaper and more
defensible.

`GET /health` is a trivial liveness check for the future VSCode extension
(Step 24) to poll before assuming the backend is up.

## 2. Fast mode — which Experiment 2 model, and why

**Chosen: `results/models/rf_v1_balanced.joblib`** — Random Forest, V1
(per-spec) features, `class_weight='balanced'`.

This was checked against `reports/exp2_model_evaluation.md`'s own criteria,
not picked for Experiment 3/4-comparison convenience (which used
`rf_v1_plain`/`svm_v1_plain` for a different reason — matching Experiment
3's own diff-only LLM context). Three separate choices, each justified from
that report:

| Choice | Alternative | Why |
|---|---|---|
| **Random Forest** | SVM | "Random Forest clearly outperforms SVM here on every metric that matters for the minority class" (§2); RF's `class_weight` is a direct, predictable lever on minority recall, where SVM's — routed through `CalibratedClassifierCV` — is not (§5). |
| **`balanced`** | `plain` | `balanced` lifts not-merged recall 0.250 → 0.425 (F1 0.333 → 0.395) for an explicit, reported accuracy cost (0.821 → 0.768, §2). A tool that always predicts "MERGE" scores *higher* accuracy while catching none of the PRs worth a second look — exactly the class-imbalance trap plan §10 warns about ("class imbalance inflates apparent SVM/RF accuracy... report minority-class recall explicitly, not just accuracy"). For a review **aid**, minority recall is the number that matters. |
| **V1** | V2 | V2 (pre-review-strict + author history) measurably *outperforms* V1 on every matched configuration (§4 — "a genuinely surprising result") and would be the better choice **if** the API always knew the author. It doesn't: V2's `author_prior_merge_rate`/`author_prior_pr_count` need a (repo, author) identity looked up against the mined dataset's own PR history, which an arbitrary incoming diff — from any contributor, in any repo, not necessarily one of the 5 mined ones — does not reliably carry. V1 is the variant computable for *any* diff. (See §4 below for how this could be revisited.) |
| — | V0 | Never a candidate: V0's `p_*` features (review count, approvals, labels) require the review process to have *already happened* — exactly the leakage `reports/exp2_model_evaluation.md` §3 exists to demonstrate is illegitimate, and doubly so for a diff nobody has reviewed yet. |

### 2.1 Computing V1 features for a diff with no `pr_id`

Every existing feature-extraction path (`src/features/feature_extraction.py`)
is keyed by `pr_id` against `data/processed/*.parquet` — it doesn't apply to
a diff that isn't a mined PR. `src/api/ml_features.py` re-derives the exact
same 28 V1 columns directly from a parsed diff:

* **M (modification)** and **T (textual)** — recomputed with the identical
  arithmetic `feature_extraction.py` uses (churn, net change, hunk counts,
  file-status counts, title/body lengths), just reading from
  `ParsedFile`/optional strings instead of DataFrame rows.
* **S (structure)** — `src/features/ast_cfg.py`'s `analyze_file(filename,
  patch)` is called *directly, unmodified* per changed file and aggregated
  exactly like `aggregate_to_pr_features` does (sum node/edge/cyclomatic
  counts, max depth, any-parseable flag). This is the one piece reused
  as-is rather than re-derived, since it already operates on a single
  `(filename, patch)` pair with no `pr_id` dependency.

One documented default where a real PR always has an answer but a bare diff
might not: `m_num_commits` defaults to **1** (not 0) when no
`commit_messages` are supplied — a diff, by definition, came from at least
one commit. Every other missing input (title, description, commit messages)
renders as empty text, matching the training pipeline's own `fillna(0)` /
"not provided" treatment.

## 3. Diff parsing (`src/api/diff_parsing.py`)

The mined dataset's `files_changed.patch` column is GitHub's per-file patch
format (hunks only, no `diff --git`/`index`/`---`/`+++` preamble) — but the
API's actual input (eventually the VSCode extension's `git diff` output, or
any caller's raw diff) is a full unified diff with those headers. So
`parse_unified_diff` splits an incoming diff on `diff --git` boundaries,
reads `new file mode` / `deleted file mode` / `rename from`/`rename to` /
`---`/`+++` lines to classify each file's status and name, and treats
everything from the first `@@` onward as that file's patch body — producing
the *exact* `(filename, status, patch)` shape `files_changed.parquet` rows
have, so `ast_cfg.analyze_file` and the whole S-feature pipeline apply
completely unmodified.

**Known, documented limitation:** filenames containing spaces or other
characters git would C-quote (`diff --git "a/has spaces" "b/has spaces"`)
are not unquoted — a pragmatic subset of `git diff`, not a general patch
parser. Not a real constraint for this project's 5 mined repos or typical
source trees.

## 4. Deep mode — the LLM design decision

The task brief flagged this explicitly as an open design choice: should
"deep mode" call Groq live per request, given quota is real, shared, and
scarce (500k tokens/day account-wide, already exhausted mid-project by the
Experiment 3/4 grids on the same calendar day, per
`reports/exp4_grid_run_status.md`)?

**Decision: yes, live per request — opt-in, cached, capped, and
gracefully-degrading.** The alternative (a static/canned fallback response
when quota is unavailable) was rejected: it would silently present
fabricated review comments as if they were real model output, which is
worse than an honest "the LLM pass is unavailable right now" signal. The
existing `CachedChatProvider` architecture (Experiments 3/4) was already
built for exactly this "spend real quota, cache forever" pattern, so deep
mode reuses it unchanged rather than inventing a second policy:

1. **Opt-in, not default.** `mode="fast"` is the default; a caller
   consciously spends quota only by passing `mode="deep"`.
2. **Disk-cached on the exact same cache the Experiment 3/4 grids used**
   (`data/llm_cache/`, content-addressed by `{model, system, messages,
   temperature, max_output_tokens}`). A repeated identical request costs
   nothing after the first call — confirmed in §6.2 below (a second,
   byte-identical request returned in ~30ms vs. the first call's live
   round-trip).
3. **Tight char caps**, reused directly from `run_exp4_grid.py`'s own
   tuned constants (`GROQ_RUN_MAX_DIFF_CHARS=900`,
   `GROQ_RUN_MAX_FILE_CHARS=400`, `GROQ_RUN_MAX_OUTPUT_TOKENS=500`) rather
   than re-deriving new margins — these were already calibrated to stay
   safely under Groq's **hard per-request** 6,000-token cap (a request over
   that ceiling gets an unrecoverable 413, not a retryable rate limit).
4. **Graceful degradation, never a 500.** `llm_review.generate_review_comments`
   catches `LLMQuotaExceededError`, `LLMAPIError`, and any other exception
   (missing `GROQ_API_KEY`, network failure) and returns a
   `DeepReviewResult` with `comments=None` and a human-readable `warning`
   instead of raising. `/review` always returns 200 with the (always-valid)
   fast-mode result plus `llm_warning` set — a Groq outage degrades the
   response, it doesn't break the endpoint. Verified in
   `tests/test_api_main.py::test_review_deep_mode_degrades_gracefully_on_llm_failure`.

### 4.1 Which Experiment 4 config, and why

**`Exp4Strategy.MULTI_TURN`** at **`Exp4ContextTier.DIFF_REPO_CONTEXT`**,
task `REVIEW_COMMENT`. From `reports/exp4_model_evaluation.md`:

* **By strategy** (§1.3, pooled over tiers): `multi_turn` and
  `self_reflection` are the *only two* strategies that ever predict
  "not merged" correctly on AI-authored code (`role_based`/`few_shot`/`cot`
  score 0.0 not-merged recall on every tier). `multi_turn` has the best
  macro-F1 of any strategy (0.49) without `self_reflection`'s accuracy
  collapse (0.375 vs. multi_turn's 0.50).
* **By context tier** (§1.2, pooled over strategies): `diff_repo_context`
  is the tier that lifts not-merged recall (0.0 → 0.4) and macro-F1 to its
  peak (0.36 → 0.50); `complete_se_context` — stacking *everything* —
  regresses back to 0.0. More context is not monotonically better here, so
  the richest tier is deliberately **not** used.
* **Honest caveat, stated plainly:** these are two *marginal* findings
  (each pooled over the other axis), not a jointly-measured `(tier,
  strategy)` cell — Experiment 4's n=3-complete-PR sample is too small to
  cross them. This pairing is the principled choice given what was actually
  measured, not a further-verified joint optimum. A future top-up run of
  Experiment 4 (more PRs, `--fetch-issues`) would let this be confirmed
  directly rather than inferred from two margins.

**Repository context needs no GitHub call.** `diff_repo_context`'s slot is
filled by `context_aug.build_lightweight_repo_context` — the same no-fetch
approximation (git hunk headings → enclosing symbols, changed-file
groupings by directory) Experiment 4's own grid run used when it chose not
to fetch full file bodies. This means deep mode works for **any** diff, not
just PRs already in the mined dataset, with zero extra network calls beyond
the one Groq request itself.

**Only review comments, not a second merge-prediction call.** Running
`Task.MERGE_PREDICTION` through the same multi-turn config was considered
and rejected for this step: it would double deep mode's live-call cost (2
tasks × 2 turns = 4 calls instead of 2) for a number the endpoint doesn't
need, since merge probability already has a reliable, free source (§2).
Comparing the ML probability against an LLM's independent merge judgment is
a plausible presentation/demo idea, but is out of scope for what plan §7.1
actually asks the endpoint to return.

## 5. API contract

```
POST /review
{
  "diff": "<unified diff, required>",
  "title": "<optional>",
  "description": "<optional>",
  "commit_messages": ["<optional>", ...],
  "repo": "<optional, e.g. 'owner/name'>",
  "mode": "fast" | "deep"      // default "fast"
}

200 OK
{
  "mode": "fast" | "deep",
  "n_files_changed": <int>,
  "merge_probability": <float 0-1>,
  "merge_prediction": "MERGE" | "CLOSE",
  "ml_model": "rf_v1_balanced",
  "features": { ...the 28 V1 feature values used... },
  "review_comments": [<string>, ...] | null,   // deep mode only
  "llm_config": "groq/llama-3.1-8b-instant multi_turn @ diff_repo_context" | null,
  "llm_warning": "<string>" | null              // set iff deep mode's LLM call failed
}

422  -- unparseable diff (no recognizable file blocks), or a schema violation
        (empty diff, invalid mode, missing required field)
```

`features` is returned deliberately (not just the bottom-line probability):
the grading rubric rewards being able to *explain* a model's output, not
just report a number, and this gives a human (or the VSCode extension's
future "why this score" panel) something concrete to inspect.

## 7. Known limitations / future work

* **Diff parser is a pragmatic subset of `git diff`**, not a full patch
  parser (§3) — fine for this project's scope, worth knowing before
  pointing it at adversarial input.
* **V2's author-history features are unused** by the API (§2) even though
  they measurably outperform V1 offline. If the VSCode extension (Step 24+)
  always operates inside one of the 5 mined repos and can supply an author
  login, a future iteration could opportunistically look up
  `author_prior_merge_rate`/`author_prior_pr_count` from the mined dataset
  and use `rf_v2_balanced` instead — a natural, currently out-of-scope
  extension, not an oversight.
* **The Exp4 `(tier, strategy)` pairing used here is not a jointly-measured
  optimum** (§4.1) — a larger Experiment 4 top-up run would let this be
  confirmed directly.
* **No LLM-vs-ML merge-probability comparison** is exposed by the endpoint
  (§4.1) — a plausible future addition for the presentation/demo, not
  required by plan §7.1.

## 8. Provider change: Groq → Qwen for live deep mode

*Added after Steps 23–27, when a live `deep`-mode call stopped working.*

### 8.1 What broke

Groq retired `llama-3.1-8b-instant`. Every live deep-mode request began
coming back as:

```
LLM call failed: Groq API error 404 (invalid_request_error):
The model `llama-3.1-8b-instant` does not exist or you do not have access to it.
```

This is not a quota problem and no amount of waiting fixes it. The model id
was pinned in `src/llm/providers.py` (`GROQ_DEFAULT_MODEL`), which was the
right thing to do for a reproducible experiment and the wrong thing to
depend on for a live service.

### 8.2 The distinction that drove the fix

The pinned id is doing **two different jobs**, and only one of them broke:

1. **As an experimental constant.** Every number in
   `results/tables/exp3_*` and `exp4_*` was measured on that model. The
   ~700 responses in `data/llm_cache/` are keyed on it. That record is
   intact and must stay reproducible.
2. **As a live service dependency.** Deep mode has to call *something that
   answers*.

Conflating the two gives two bad options: leave deep mode broken to protect
the record, or repoint the constant and silently make every "reproduction"
of Labs 3/4 a new measurement against a different model. Separating them
gives the actual fix — change the live path, leave the experimental default
alone:

| | Provider | Why |
|---|---|---|
| Live deep mode (`src/api/llm_review.py`) | **Qwen** (`qwen-plus`) | Has to answer. Config unchanged; only the model differs. |
| `run_exp3_grid.py` / `run_exp4_grid.py` | **Groq** (still the `--provider` default) | Cache is keyed on the retired model, so a `groq` re-run replays Labs 3/4 from disk — exactly, for free, with no key. |

The cache key includes `model`, so this is enforced by construction rather
than by discipline: a Qwen run cannot read a Groq entry (which would
silently mix providers inside one result set) and cannot overwrite one
(which would destroy the record). `tests/test_llm_providers_qwen.py`
asserts both directions, and a test reads the `--provider` default out of
each runner's AST so the grid default cannot drift back without failing.

### 8.3 Why Qwen

DashScope publishes an OpenAI-compatible `chat/completions` endpoint, so
`QwenProvider` is the same request shape `GroqProvider` already builds and
the same response `_parse_chat_completion` already reads — the whole
provider is a base URL, a key and a 429 dialect, not a second response
format to maintain. `qwen-plus` is the balanced tier; `qwen-turbo` is the
closer analogue to the retired 8B model if quota binds (`QWEN_MODEL`).

### 8.4 What this does *not* claim

Experiment 4 chose `multi_turn` @ `diff_repo_context` on evidence gathered
from `llama-3.1-8b-instant`. **Whether that is also the best config for Qwen
is untested** — answering it means re-running the Exp-4 grid with
`--provider qwen`, which is a new measurement with its own quota cost. What
is carried over is the *configuration*, not a claim that it remains optimal.

So deep mode's `llm_config` label now names the model that actually
answered (`qwen/qwen-plus multi_turn @ diff_repo_context`), and the
extension's panel shows it. A result can never be mistaken for one of
Experiment 4's cells.

### 8.5 Two hardening changes the outage argued for

* **`CODE_REVIEW_AI_LLM_PROVIDER`** (`qwen` | `groq` | `gemini`), plus
  `QWEN_MODEL` and `DASHSCOPE_BASE_URL`. A pinned model id has now been
  retired upstream once during this project's life; the next time should
  not need a code edit.
* **Warnings name the provider that actually failed.** The quota path was
  the literal string `"Groq quota exhausted"` regardless of who was called
  — which, after this change, would have been an actively misleading
  message rendered in the extension's panel.

### 8.6 Verification

* **451 tests pass** (415 before; 36 added — a 27-test
  `tests/test_llm_providers_qwen.py` plus provider-selection and
  regression tests in `tests/test_api_llm_review.py`). `ruff` clean.
* **The endpoint is real, and the request shape is right.** A live
  round-trip to DashScope with a deliberately invalid key returns
  `Qwen API error 401 (invalid_request_error): Incorrect API key provided`
  — a 404 would have meant a wrong URL and a 400 a malformed body, so 401

* **Deep mode still degrades instead of failing.** With no key set, a real

* **Not verified: a live Qwen generation.** No DashScope key is configured
